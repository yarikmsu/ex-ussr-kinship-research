# Как уроки исследований попадают в форк

Порядок переноса урока из исследования в дополнения форка. Устройство дополнений и слияние с каноническим репозиторием — `references/fork/README.md`. Волна — партия уроков, которую переносят одной веткой и одним PR.

## 1. Записать урок

- Уроки о самом навыке записывайте в частный журнал вне рабочей копии навыка, например `~/kinship-cases/skill-lessons.md`. Журнал только дописывают в конец датированными блоками. Если план ссылается на строки журнала по номерам, эти строки не правят; неизменность начала файла проверяйте хешем.
- В журнале урок пишут как есть, с деталями дела. Обезличивают его при переносе в репозиторий, а не при записи.
- Исключение — живые люди, а также те, кто может быть жив или чей статус неизвестен: только имя и родство, без контактов, адресов и номеров документов. Удалить запись по просьбе пользователя или ради приватности можно; после этого обновите хеш и ссылки на номера строк.
- Урок, который в журнале повторяется, закрывайте инструментом — скриптом или проверкой, — а не ещё одной фразой.

## 2. Сверить с текущим текстом

- До сверки проверьте, есть ли в каноническом репозитории изменения, ещё не влитые в форк: `git fetch origin && git fetch upstream && git log --oneline origin/main..upstream/main`. Если есть:
  - сообщите о них пользователю: новая версия может уже покрыть уроки, и RED (раздел 3) по старому тексту даст ложное «нужна правка»;
  - с его согласия сначала влейте их в `main` форка по `references/fork/README.md`, «Обновление из канонического репозитория», и начните ветку волны от обновлённого `main`;
  - без согласия сверяйте по текущему тексту и отметьте это у вердиктов.
- Ищите урок и в основном тексте навыка, а не только в `references/fork/`. Каждому уроку дайте вердикт со ссылкой «файл, раздел»:
  - COVERED — уже сказано;
  - LOCAL — касается только одного дела;
  - PARTIAL-MISSING — сказано не всё;
  - MISSING — не сказано.
- Переносите только недостающую часть: узкая фраза форка перекрывает более точную фразу основного текста.
- Когда вердикты волны окончательны — после сверки, а для уроков с кейсом после последнего RED (раздел 3), — допишите в конец журнала датированный блок. По каждому уроку: вердикт; «файл, раздел», где урок уже сказан или куда его переносят; итог RED, если он был; решение — перенести, сузить или не переносить; волна — имя ветки. Номер PR и итог — влит или закрыт — допишите следующим блоком. Записи уроков не правьте. Без такого блока уроки, которые волна не взяла, теряются: следующая сверка не отличит их от проверенных.

## 3. Проверить кейсом до правки

- Кейс — запрос и ожидаемые шаги в `evals/fork-lessons.yaml`, id с префиксом `fork_`. Он проверяет конкретный шаг урока, а не общий вывод, который модель делает и без навыка.
- RED: свежий исполнитель отвечает на запрос кейса по навыку без правки. GREEN: по навыку с правкой. Исполнитель читает только `SKILL.md` и `references/`, без `evals/` и `tests/`.
- Ловушку прячьте в обычных данных и спрашивайте о следующем шаге, а не о самой ловушке: если запрос называет ловушку, модель решает кейс и без навыка. Кейсом лучше всего проверять уроки о том, когда прервать чтение ради проверки: этот шаг модель без навыка пропускает.
- Вымышленные имена и числа кейса проверяйте до записи в файл. Папки дел — у пользователя; если путь неизвестен, спросите.
  - Имена — подайте текст кейса на вход `python3 scripts/privacy_scan.py check --patterns <файл>` (шаблоны — раздел 4) и ищите основу без окончания `grep -rIi` по папкам дел: сканер пропускает частые имена. Без `-F`: в оболочке агента `grep` бывает подменён на ugrep, а тот с `-F -i` не сворачивает регистр кириллицы. Буквы с вариантами пишите классом (`[еёѣ]`, `[иі]`), латинскую запись ищите отдельно.
  - Числа (листы, номера приходов, счёт снимков, возраст, годы, дни дат, концы диапазонов) — `grep -rIE '(^|[^0-9])0*<число>([^0-9]|$)'` по папкам дел, а не `-w`: для `-w` приклеенные буквы («об.», «г.») — часть слова. Диапазон проверяйте с дефисом и с тире. Текст PDF `grep` не видит — сначала `pdftotext`.
  - Если имя или число нашлось и рядом в деле тот же вид записи или та же ситуация, замените его, даже если совпадение одно.
- Если RED уже выполняет ожидаемое, правка не нужна или её надо сузить: замените кейс или перенесите только то, чего RED не сделал.
- Правку пишите после RED:
  - пункт стройте так: условие → действия по порядку → толкование. Фраза без условия не срабатывает, даже если исполнитель прочитал раздел; исполнитель, который отвечает кратко, упускает конец длинного пункта;
  - условие с оговорками держите в одном месте, а в других файлах ставьте короткий указатель: повод и ссылку, без оговорок («прежде чем X — файл, раздел»). Копии оговорок расходятся при следующей правке. Исключение — согласие на публикацию и защита живых: их повторяйте в каждом месте, откуда агент может начать;
  - если дополнение отменяет или сужает правило основного текста, кладите его в `references/fork/<имя>.md` под заголовок того же раздела с пометкой «— дополнения форка» (`references/fork/README.md`, «Как читать»); правило из `SKILL.md` — в его раздел «Дополнения форка»;
  - в таком пункте точно перескажите основной текст: «`<файл>`, раздел «<заголовок>», советует X без оговорки; X годится, только если …». Раздел называйте заголовком, а не номером: номера сбиваются, когда в основном тексте добавляют раздел. По неточному пересказу при слиянии решат, что основной текст уже покрывает дополнение, и удалят его.

## 4. Перед push

- Push и PR — в форк и в канонический репозиторий — только после явного согласия пользователя: это публикация. Заголовок и описание PR проверяйте на приватность так же, как сообщения коммитов.
- `python3 -m unittest discover -s tests` и `git diff --check`.
- Проверка приватности: каждый коммит и его сообщение сверяются с шаблонами имён, мест и номеров дел, которые хранятся вне репозитория. Push публикует всю историю ветки, а не только итог, поэтому проверяйте `git log -p --no-color --format= main..HEAD | python3 scripts/privacy_scan.py check --patterns <файл> --diff` и `git log --format=%B main..HEAD | python3 scripts/privacy_scan.py check --patterns <файл>`; `git diff main` видит только итог и пропустит имя, которое один коммит добавил, а другой убрал. Как собрать шаблоны — `references/fork/privacy-and-safety.md`, раздел 8. Шаблоны знают ID и шифры из реестров и следующие номера серий ID; номера из одних цифр и номера, которых нет в реестрах, ищет ревью.
- Ревью свежим исполнителем. Он ловит то, чего не ловит список:
  - реальные числа дела в примерах, сообщениях коммитов, заголовке и описании PR (дайте ревьюеру черновик до создания PR);
  - приёмы, которые обходят защитные фильтры вывода;
  - правила форка, которые из-за приоритета снимают защиту живых;
  - в PR слияния с каноническим репозиторием — дополнения, которые сверка по `references/fork/README.md` («После каждого слияния…», шаги 1–2) пропустила. Дайте ревьюеру `git diff <слияние>^1...<слияние>^2 -- SKILL.md references/ evals/`, файлы дополнений из списка шага 1 целиком и раздел «Дополнения форка» из `SKILL.md`.
- Конкретику дела ловите до первого push: после перезаписи ветки старые коммиты остаются видны в истории PR.

## 5. Рабочая копия и ветки

Рабочая копия, из которой агент загружает навык, всегда стоит на `main`. Ветки для PR держите в отдельном `git worktree`: иначе при следующем запуске загрузится текст ветки без части дополнений. Папку worktree держите вне `.claude/skills/`: копия с `SKILL.md` там может загрузиться как ещё один навык. Команды в worktree пишите через `git -C <папка>` или `cd <папка> && …` одной строкой: отдельный `cd` у агента на следующие команды может не подействовать.

## 6. Канонический репозиторий

- Предлагайте туда маленькие PR по 1–2 пункта: описание на английском, обезличенное «Why», без отпечатков дела и без рецептов массовой выгрузки. Версию и changelog правит мейнтейнер. Наблюдения оформляйте как «По наблюдению участника ДД.ММ.ГГГГ».
- Что делать с дополнением после принятия PR и после каждого слияния — `references/fork/README.md`.
