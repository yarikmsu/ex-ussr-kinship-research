# Как уроки исследований попадают в форк

Порядок переноса урока из исследования в дополнения форка. Устройство дополнений и слияние с каноническим репозиторием — `references/fork/README.md`.

## 1. Записать урок

- Уроки о самом навыке записывайте в частный журнал вне рабочей копии навыка, например `~/kinship-cases/skill-lessons.md`. Журнал только дописывают в конец датированными блоками. Если план ссылается на строки журнала по номерам, эти строки не правят; неизменность начала файла проверяйте хешем.
- В журнале урок пишут как есть, с деталями дела. Обезличивают его при переносе в репозиторий, а не при записи.
- Исключение — живые люди, а также те, кто может быть жив или чей статус неизвестен: только имя и родство, без контактов, адресов и номеров документов. Удалить запись по просьбе пользователя или ради приватности можно; после этого обновите хеш и ссылки на номера строк.
- Урок, который в журнале повторяется, закрывайте инструментом — скриптом или проверкой, — а не ещё одной фразой.

## 2. Сверить с текущим текстом

- Ищите урок и в основном тексте навыка, а не только в `references/fork/`. Каждому уроку дайте вердикт со ссылкой «файл, раздел»:
  - COVERED — уже сказано;
  - LOCAL — касается только одного дела;
  - PARTIAL-MISSING — сказано не всё;
  - MISSING — не сказано.
- Переносите только недостающую часть: узкая фраза форка перекрывает более точную фразу основного текста.

## 3. Проверить кейсом до правки

- Кейс — запрос и ожидаемые шаги в `evals/fork-lessons.yaml`, id с префиксом `fork_`. Он проверяет конкретный шаг урока, а не общий вывод, который модель делает и без навыка.
- RED: свежий исполнитель отвечает на запрос кейса по навыку без правки. GREEN: по навыку с правкой. Исполнитель читает только `SKILL.md` и `references/`, без `evals/` и `tests/`.
- Если RED уже выполняет ожидаемое, правка не нужна или её надо сузить: замените кейс или перенесите только то, чего RED не сделал.

## 4. Перед push

- Push и PR — в форк и в канонический репозиторий — только после явного согласия пользователя: это публикация. Заголовок и описание PR проверяйте на приватность так же, как сообщения коммитов.
- `python3 -m unittest discover -s tests` и `git diff --check`.
- Проверка приватности: diff и сообщения коммитов сверяются со списком имён, мест и номеров дел, который хранится вне репозитория.
- Ревью свежим исполнителем. Он ловит то, чего не ловит список:
  - реальные числа дела в примерах;
  - приёмы, которые обходят защитные фильтры вывода;
  - правила форка, которые из-за приоритета снимают защиту живых.
- Конкретику дела ловите до первого push: после перезаписи ветки старые коммиты остаются видны в истории PR.

## 5. Рабочая копия и ветки

Рабочая копия, из которой агент загружает навык, всегда стоит на `main`. Ветки для PR держите в отдельном `git worktree`: иначе при следующем запуске загрузится текст ветки без части дополнений.

## 6. Канонический репозиторий

- Предлагайте туда маленькие PR по 1–2 пункта: описание на английском, обезличенное «Why», без отпечатков дела и без рецептов массовой выгрузки. Версию и changelog правит мейнтейнер. Наблюдения оформляйте как «По наблюдению участника ДД.ММ.ГГГГ».
- Что делать с дополнением после принятия PR и после каждого слияния — `references/fork/README.md`.
